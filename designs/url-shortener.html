Design a URL Shortener

Turn a long URL into seven characters, then redirect hundreds of thousands of clicks a second. The interesting parts are generating codes that never collide and keeping a 100:1 read-heavy path fast when one link goes viral.

  • 100:1 read : write
  • ~350K redirects/s peak
  • base62 · 7 chars
  • cache-aside
  • 301 vs 302
01

Requirements

A classic warm-up question that turns hard on follow-ups. Get the read/write asymmetry and the redirect semantics on the table early — the rest of the design follows from them.

Functional

  • Shorten — long URL in, short unique URL out.
  • Redirect — short URL sends the browser to the original.
  • Custom alias — sho.rt/launch-2026, if available.
  • Expiry — optional; expired links stop working.
  • Click analytics — counts by day, country, referrer.
  • Manage — list, disable and delete my links.

Non-functional

  • Fast redirects — p99 < 50 ms server-side; this is the product.
  • Highly available reads — a dead short link breaks every page it is printed on.
  • Unique codes — never two URLs behind one code.
  • Durable — links live for years.
  • Not guessable — codes should not be enumerable.
  • Analytics may lag — eventually consistent, seconds to minutes.

Out of scope

  • Link-in-bio pages and QR code design
  • Billing and plan management
  • Editing the destination of an existing link
  • Full malware-scanning pipeline internals
  • User accounts and authentication

    Scaling

    Reads Layers of cache

    Browser (for 301s) → CDN edge → in-process LRU for the hottest codes → Redis → database. Each layer only sees what the one before it missed. Redirect servers are stateless and scale horizontally behind a load balancer.

    Writes No hot spots

    Writes are only ~1K/s, so the store is sized for data volume, not write throughput. Partitioning by a hash of code spreads new links evenly — which is another reason to scramble IDs: sequential keys on a range-partitioned store would all land on the last partition.

    Regions Read local, write anywhere

    Replicate the URL store to every region so redirects are always local. Give each region its own ID blocks (or a region digit in the ID) so creates never need cross-region coordination. A link created in one region is readable elsewhere after replication lag — retry at a stronger consistency on a miss.

    Failure modes

    What breaksEffectMitigation
    Redis shard downMisses for that shard’s codes flood the database.Request coalescing, in-process hot cache, replicas per shard; DB capacity sized for a cache-shard loss, not zero misses.
    Viral link (hot key)One code at 100K+ req/s on one cache shard.Hot-key detection, local caching in every redirect instance, edge caching with a short TTL.
    Coordinator downNo new ID blocks can be leased.Servers keep allocating from the block they hold; prefetch the next block early. A 1M block lasts each server ~15 minutes at peak.
    Write server crashesThe rest of its ID block is never used.Harmless — gaps in the sequence don’t matter with trillions of codes.
    Kafka unavailableClick events can’t be published.Bounded local buffer, then drop and count. Redirects carry on unaffected.
    Phishing link reportedMalicious redirect served from caches.Disable in the DB, publish an invalidation event that evicts Redis, local and edge entries; return 410 or a warning page.
    Region outageUsers routed there can’t resolve links.Health-checked DNS / anycast fails over to the next region, which already holds a full replica.
    06

    Interviewer asks…

    Likely follow-ups. Try answering out loud before you expand each one.

    Q1Why not just hash the long URL and take the first 7 characters?

    CODE GENERATION

    Truncating a hash throws away most of its bits, so different URLs will collide. At 182B links in a 3.5T space, roughly 1 in 20 new codes would hit an existing one by year five. Every insert then needs a read to check, plus a retry with a salt on conflict — and two concurrent inserts can still race unless the write is conditional.

    The one real benefit — the same URL always gets the same code — is something you usually don’t want anyway (see Q5). A counter with base62 encoding never collides, so the insert is a blind write.

    Q2How do many write servers generate unique IDs without talking to each other on every request?

    DISTRIBUTED IDS

    Range leasing. A coordinator (etcd, ZooKeeper, or a single DB row updated with compare-and-set) hands out blocks: server A gets 1,000,000–1,999,999, server B gets 2,000,000–2,999,999. Each server increments locally with an atomic counter.

    • The coordinator is touched once per block, not per link — and prefetching the next block keeps it off the request path entirely.
    • If a server dies mid-block, the unused IDs are simply skipped. Gaps cost nothing.
    • Alternative with no coordinator: Snowflake-style IDs (time + machine + sequence), at the cost of longer codes.
    Q3301 or 302?

    REDIRECT SEMANTICS

    301 Moved Permanently is cacheable by default — the browser may never ask you again. That saves load, but you lose those clicks from analytics and can’t disable the link for anyone who already followed it.

    302 Found (or 307) is temporary — every click reaches you, so analytics are complete and you keep control, at the cost of more traffic.

    A product whose value is analytics and link management uses 302 with a short Cache-Control max-age. A pure “make it short” service with no analytics could use 301. Either way, say why — that’s the point of the question.

    Q4One link gets 1 million clicks per second. What breaks and how do you fix it?

    HOT KEYS

    The cache shard holding that code is the bottleneck — sharding spreads different keys, not one key. If that shard fails, every instance misses together and the database gets the whole load (thundering herd).

    • Edge / CDN caching with a short TTL absorbs most of it before it reaches you.
    • In-process cache in each redirect instance for detected hot codes — the load is now spread across all instances.
    • Request coalescing: on a miss, one DB read per key per instance; everyone else waits for that result.
    • Replicate the hot key across several cache shards (u:{code}#0..7) and read a random copy.
    Q5Two users shorten the same URL. Should they get the same code?

    DEDUPLICATION

    Usually no. Sharing a code means sharing click analytics, one user can’t delete or expire it without affecting the other, and the system needs a second index (long_url → code) that is as large as the main table.

    Reasonable compromise: dedupe only within the same user account and the same settings (expiry, alias), using a hash of the normalised URL as the lookup key. Across users, storage is cheap — 500 bytes per link — so duplicates cost almost nothing.

    Q6How do custom aliases work without a race between two people picking the same one?

    CUSTOM ALIASES

    Treat the alias as the primary key and insert with a conditional write — INSERT … IF NOT EXISTS (Cassandra LWT, DynamoDB condition expression, or a unique constraint in SQL). Exactly one insert wins; the other gets 409 Conflict. No separate “check, then write”.

    • Aliases share the namespace with generated codes, so keep them distinguishable — e.g. require a hyphen or a minimum length that generated codes never use, or reserve a character.
    • Block reserved words (api, login, admin) and offensive terms.
    Q7How do you stop people abusing the service for spam and phishing?

    ABUSE

    • At creation: rate limits per user and IP, an in-memory domain blocklist, and stricter rules for anonymous users.
    • After creation: asynchronous scanning with reputation services; a flagged link is disabled and its caches invalidated.
    • At redirect: show an interstitial warning page for suspicious destinations instead of redirecting straight through.
    • Unguessable codes, so attackers can’t enumerate private links, plus abuse reporting with fast takedown.

    The redirect domain’s reputation is the business: if browsers and email providers start flagging it, every customer’s links break.

    Q8How do you count clicks accurately at 116K per second?

    ANALYTICS

    Never increment a counter in the URL row per click — that turns the read path into a write path and creates hot rows for popular links. Instead:

    • Emit an event per click to Kafka, asynchronously, keyed by event_id so a viral link doesn’t create a hot partition.
    • A stream job dedupes by event_id, filters bots, and writes per-minute rollups to an OLAP store.
    • Unique visitors via HyperLogLog sketches: ~1% error in a few KB per link per day.

    Be upfront about the gaps: edge-cached redirects and dropped events under overload mean the count is “very close”, not exact. If exact counts matter, ship CDN logs into the same pipeline.

    Q9What happens when a link expires? Do you reuse the code?

    EXPIRY

    Enforce expiry at read time — the redirect checks expires_at and returns 410 Gone — so it’s exact to the second regardless of cleanup. Separately, a background sweeper or the database’s native TTL deletes expired rows to reclaim space.

    Don’t reuse codes. A printed flyer or an old bookmark would silently start pointing at someone else’s URL — a security problem, not just a bug. With 3.5 trillion 7-character codes there is no shortage to justify the risk.

    Q10SQL or NoSQL for the URL store?

    STORAGE CHOICE

    The workload is a single huge table, lookup by primary key, almost no updates, no joins, ~6K reads/s after the cache and ~1K writes/s — and ~90 TB over five years. That points to a horizontally partitioned key-value or wide-column store (Cassandra, DynamoDB, or similar): linear scaling, multi-region replication built in.

    Sharded MySQL / Postgres is a perfectly good answer too — you get unique constraints and transactions for aliases — but you own resharding as data grows. Either way, the deciding factors to state are: access pattern, data volume, and how much operational work you’re willing to take on.
