Design a Rate Limiter

Let a caller make N requests per window and politely refuse the rest — correctly under concurrency, across many servers, and without becoming the slowest part of every request.

  • LLD · classes & interfaces
  • token bucket
  • Strategy pattern
  • atomic Redis script
  • < 2 ms overhead
01

Requirements

In an LLD round, start by pinning down behaviour and the extension points — the interviewer is checking whether your classes can absorb the next requirement without a rewrite.

Functional

  • Limit by identity — API key, user, tenant or IP, per route.
  • Configurable rules — e.g. 100 req/min for free plan, 1,000 for paid; changeable at runtime.
  • Pluggable algorithms — token bucket, fixed window, sliding window.
  • Clear rejection — 429 with Retry-After and remaining-quota headers.
  • Weighted requests — an expensive call can cost more than one permit.
  • Works across servers — one limit shared by the whole fleet.

Non-functional

  • Low overhead — a couple of milliseconds at most on every request.
  • Thread-safe — no lost updates when many threads hit the same key.
  • Accurate enough — never wildly over the limit; small, bounded error is acceptable.
  • Fault tolerant — if the counter store is down, the API stays up.
  • Memory bounded — state for idle callers is evicted.
  • Testable — time is injected, not read from a global clock.

Out of scope

  • DDoS mitigation at the network layer
  • Authentication (we receive an identity)
  • Billing / monthly usage quotas
  • Admin UI for editing rules
  • Client-side throttling libraries

Deep dive

Class design

Small interfaces at the seams that change: the algorithm, the storage, and how a caller is identified. Everything that crosses a seam is an immutable value.

RateLimiter «interface»
  • tryAcquire(key, rule, permits)→ Decision
The only thing the filter knows about. One method, non-blocking, never throws for a denial. Implementations: TokenBucketLimiter, FixedWindowLimiter, SlidingWindowLimiter.
RateLimitRule immutable value
  • idString
  • algorithmenum
  • capacitylong · max burst
  • refillPerSecdouble
  • windowDuration · window algorithms
Pure configuration. Holds no counters, so it can be swapped at runtime.
Decision immutable value
  • allowedboolean
  • remaininglong
  • retryAfterDuration
Richer than a boolean so the filter can set headers. Built via Decision.allow(n) / Decision.deny(wait).
CounterStore «interface»
  • consume(key, rule, permits)→ Decision
Hides where state lives. The operation is “refill and take” as one atomic unit — never separate get and set. Implementations: RedisStore, LocalStore, and a FallbackStore decorator.
KeyResolver «interface»
  • resolve(request)→ String
Implementations: ApiKeyResolver, UserIdResolver, IpResolver, plus a composite that tries them in order.
RuleRepository class
  • find(identity, route)→ RateLimitRule
  • reload(newRules)atomic swap
  • currentvolatile RuleSet
Read on every request, written rarely: an immutable snapshot behind one volatile reference.

Pattern Strategy

Each algorithm is a RateLimiter. The rule picks one; the filter never branches on algorithm type. Adding “leaky bucket” touches zero existing classes — the open/closed principle, concretely.

Pattern Decorator

FallbackStore wraps a primary and a secondary CounterStore and adds the timeout and circuit breaker. Metrics and shadow mode are further decorators around RateLimiter — behaviour added without editing the algorithms.

Pattern Chain of responsibility

The filter sits in the request chain and either passes the request on or ends it with a 429. Several limits (per user, per IP, global) are just several rules checked in order — stop at the first denial.

Code sketch

JAVAIn-memory token bucketthread-safe
public interface RateLimiter {
  Decision tryAcquire(String key, RateLimitRule rule, int permits);
}

/** One bucket per key. All state changes happen under the bucket's own lock. */
final class TokenBucket {
  private double tokens;
  private long lastRefillNanos;

  TokenBucket(RateLimitRule rule, long now) {
    this.tokens = rule.capacity();      // start full
    this.lastRefillNanos = now;
  }

  synchronized Decision tryConsume(RateLimitRule rule, int permits, long now) {
    // Lazy refill: no background thread, just maths on each call.
    double perNano = rule.refillPerSec() / 1_000_000_000.0;
    tokens = Math.min(rule.capacity(), tokens + (now - lastRefillNanos) * perNano);
    lastRefillNanos = now;

    if (tokens >= permits) {
      tokens -= permits;
      return Decision.allow((long) tokens);
    }
    long waitNanos = (long) Math.ceil((permits - tokens) / perNano);
    return Decision.deny(Duration.ofNanos(waitNanos));
  }
}

final class TokenBucketLimiter implements RateLimiter {
  private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
  private final LongSupplier clock;     // System::nanoTime in prod, a fake in tests

  TokenBucketLimiter(LongSupplier clock) { this.clock = clock; }

  @Override
  public Decision tryAcquire(String key, RateLimitRule rule, int permits) {
    long now = clock.getAsLong();
    TokenBucket bucket = buckets.computeIfAbsent(key, k -> new TokenBucket(rule, now));
    return bucket.tryConsume(rule, permits, now);
  }
}
The lock is per bucket, so different callers never contend. computeIfAbsent guarantees one bucket per key even when two threads arrive together. A real version also evicts idle buckets (see below).

-- ARGV    = capacity, refill_per_sec, permits

local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local permits  = tonumber(ARGV[3])

-- Use the Redis server's clock so app servers with
-- skewed clocks can't disagree about how much to refill.
local t   = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)   -- ms

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity        -- new key: full
local ts     = tonumber(state[2]) or now

-- Lazy refill, capped at capacity.
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)

local allowed = tokens >= permits
if allowed then
  tokens = tokens - permits
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- Idle buckets expire once they would be full again anyway.
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)

local retry_ms = 0
if not allowed then
  retry_ms = math.ceil((permits - tokens) / rate * 1000)
end
return { allowed and 1 or 0, math.floor(tokens), retry_ms }
Redis runs a script start-to-finish with nothing interleaved, so the read-modify-write is atomic without any lock. Load it once and call it by hash (EVALSHA). The {abc123} hash tag keeps a caller’s keys on one cluster shard.

Concurrency

The bug Check-then-act

Two threads read tokens = 1, both see “enough”, both subtract. Two requests pass on one token. Any design where the check and the update are separate steps has this race — in memory or over the network.

In one process Lock small, or don’t lock

A lock per bucket (as above) is short and uncontended across callers. A single global lock would serialise every request. For hot keys, replace the lock with a compare-and-set loop on an immutable (tokens, timestamp) state — lock-free, retries only on a real collision.

Across processes One atomic command

Push the whole decision into the store: a Lua script, or INCR for window counters (atomic by itself). Avoid distributed locks here — they add round trips, and a crashed holder blocks the key until the lock expires.

Interviewer asks…

Likely follow-ups. Try answering out loud before you expand each one.

Q1Two requests for the same key arrive at the same instant with one token left. Walk me through what happens.

RACE CONDITIONS

In one process: both threads find the same TokenBucket (computeIfAbsent guarantees a single instance) and call a synchronized method. One enters, refills, takes the token, leaves 0. The second then enters, sees 0, is denied. Correct because check and decrement are inside one critical section.

Across servers: both send the Lua script to Redis. Redis executes scripts one at a time, so the outcome is the same — one allowed, one denied.

What breaks it: reading the count, deciding in application code, then writing it back. Name that as check-then-act and you’ve answered the real question.

Q2Why token bucket? When would you choose something else?

ALGORITHM CHOICE

Real clients are bursty — a page load fires ten calls at once, then nothing. Token bucket allows that burst (up to capacity) while holding the long-run average, with two numbers of state and O(1) work.

  • Strict “N per window, no bursts” (login attempts, SMS sends): sliding window log for exactness at low limits, sliding window counter at high volume.
  • Downstream needs a smooth rate: leaky bucket, which queues and drains at a constant pace.
  • Rough daily quota: fixed window — simplest, and edge bursts don’t matter at that scale.
Q3A Redis call on every request is too slow for us. Now what?

REDUCING STORE CALLS

Trade a little accuracy for far fewer round trips:

  • Token leasing: a server takes, say, 50 tokens from the shared bucket in one call and spends them locally. Worst-case over-allowance is the sum of unspent leases, so size the lease as a small fraction of the limit.
  • Local deny cache: once the store says “empty until T”, reject locally until T. Abusive keys — the busiest ones — stop costing store calls at all.
  • Async sync: count locally and push deltas every 100 ms or so; fine for soft limits.

Also check the basics first: connection pooling, pipelining, and Redis in the same zone. One millisecond is usually acceptable.

Q4Redis is down. Do you fail open or fail closed?

FAILURE POLICY

It depends on what the limit protects, so make it a property of the rule rather than a global switch:

  • Fail open for ordinary API fairness limits — availability matters more than perfect fairness for a few minutes.
  • Fail closed for security or cost limits: login attempts, password reset, anything that spends money per call.
  • Better than either: fall back to per-server local limits so there is still some ceiling, and rely on other defences (autoscaling, load shedding, circuit breakers) for the rest.

Whichever you choose, put a tight timeout and a circuit breaker on the store so a slow Redis doesn’t become a slow API.

Q5We have 10 million distinct API keys. How much memory is this, and how do you keep it bounded?

MEMORY

Token bucket state is two numbers. In Redis, a small hash plus the key name is on the order of 100–150 bytes, so 10M active keys is roughly 1–1.5 GB — fine for one node, comfortable when sharded.

But you rarely hold all of them: a bucket that has been idle long enough to be full again carries no information — deleting it and recreating it full gives the same result. So set a TTL of about twice the time-to-full, and only recently active callers occupy memory.

In-process, use a size-bounded cache with expire-after-access instead of a bare map. Sliding window log is the one to avoid at this scale — it stores a timestamp per request.

Q6How do you support several limits at once — per user, per IP, and a global cap?

MULTIPLE RULES

RuleRepository returns a list of applicable rules, each with its own key. The filter checks them all and denies if any denies, returning the longest retryAfter.

The subtlety: if rule 1 allows (and takes a token) but rule 2 denies, the caller was charged for a request that never ran. Options:

  • Check all rules in one Lua script — take tokens only if every bucket has enough. Requires the keys to live on the same shard (hash tags).
  • Order rules from most to least likely to deny, and accept the small leak.
  • Refund on later denial — a second call, and not atomic.
Q7App servers have slightly different clocks. Does that matter?

TIME

Yes, if each server passes its own timestamp to shared state. A server whose clock is 500 ms ahead refills tokens that haven’t been earned; the next call from a server that is behind computes negative elapsed time.

Fixes: take time from one source — the store’s own clock (TIME inside the script) — and clamp elapsed time to be non-negative. For local buckets use a monotonic clock, not wall-clock time, so NTP corrections and DST changes can’t move it backwards.

And inject the clock as a dependency: that is what makes the limiter testable without sleeping.

Q8How would you test this?

TESTING

  • Unit tests with a fake clock: start full, drain, advance time by exactly one refill interval, assert one more request passes. No sleep(), no flaky tests.
  • Boundary cases: capacity 0, permits greater than capacity (must never be allowed — fail fast), time going backwards, very long idle periods (no overflow, cap at capacity).
  • Concurrency test: N threads behind a latch fire at one bucket with K tokens and a frozen clock; assert exactly K were allowed. Run it thousands of times.
  • Contract tests shared by every CounterStore implementation, run against a real Redis in a container for the Lua script.
  • Shadow mode in production: log would-be denials before enforcing a new rule.
Q9What should a client do when it gets a 429 — and what do you send to help it?

API CONTRACT

Send 429 Too Many Requests with Retry-After (seconds), plus quota headers on every response — limit, remaining, and time to reset — so clients can slow down before hitting the wall. Include a small JSON body naming the rule that was hit; it saves support tickets.

The client should wait at least Retry-After, then retry with exponential backoff and jitter so that a fleet of blocked clients doesn’t return in one synchronised wave. Only retry idempotent requests automatically.

Don’t use 503 for this: 429 says “you are over your limit”, 503 says “the service is unhealthy” — monitoring and clients treat them differently.

Q10How would you extend this to limit concurrent requests instead of request rate?

EXTENSIBILITY

A concurrency limit is a semaphore, not a rate: acquire on entry, release on completion. It doesn’t fit tryAcquire alone because something must be given back.

Extend the design rather than bend it: have tryAcquire return a Permit that is AutoCloseable. For rate algorithms close() does nothing; for the concurrency limiter it releases the slot. The filter wraps the downstream call in try-with-resources, so the release happens even on exceptions.

The distributed version needs a lease with expiry (a sorted set of request IDs scored by deadline), otherwise a crashed server leaks its slots forever.
