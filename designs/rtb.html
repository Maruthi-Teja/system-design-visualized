Design an Ad-Serving / Real-Time Bidding System

A page loads, an auction runs across a dozen companies, and an ad appears — all in under 100 ms. Step through the request path, then follow the events that pay for it.

  • p99 < 100 ms
  • ~1M QPS bid requests
  • OpenRTB 2.x
  • first-price auction
  • Kafka → Flink → Druid
01

Requirements

Scope it first. We cover the full request path, and go deep on the DSP bidder — the component that must answer a firehose of bid requests inside a hard deadline — plus the event pipeline behind it.

Functional

  • Run an auction per ad slot — SSP → exchange → DSPs → winner’s creative back to the page.
  • Target — match campaigns on geo, device, audience segment, time, frequency cap.
  • Respect budgets — never (meaningfully) overspend; pace spend across the day.
  • Price each bid — predicted value → bid, per impression.
  • Track — wins, impressions, clicks as billable events.
  • Report — near-real-time dashboards; exact numbers for invoices.

Non-functional

  • Latency — p99 < 100 ms end-to-end; the bidder itself gets ~20–30 ms.
  • Throughput — ~1M QPS bid requests at peak, spiky by time of day.
  • High availability — 99.9%+; a down bidder earns nothing, a slow one is as good as down.
  • Consistency — eventual is fine for reporting; budgets need bounded error; billing must be exact after reconciliation.
  • Durability — never lose a billable event.

Out of scope

  • Campaign-management UI and creative review workflow
  • Training the bid model (we only serve it)
  • Building audience segments (we only read them)
  • Cookie-sync / identity resolution details
  • Payments and invoicing systems

Scaling

Bidders Stateless, shared-nothing

Every bidder holds the full campaign index and model in memory and needs only one remote read (the user profile). So the fleet scales linearly behind an L4 load balancer; autoscale on CPU and p99, not just QPS.

Keep the hot path allocation-light (pooled buffers, pre-parsed structs) — a GC pause is a batch of missed auctions.

State Push, don’t pull

Campaign changes flow SQL → change stream → bidders as versioned deltas; a new bidder bootstraps from a snapshot then tails the stream. The profile store is sharded by user ID with replicas in each region.

Budget is the one piece of shared mutable state — and it is deliberately kept off the request path.

Pipeline Scale by partition

Kafka topics are partitioned by bid_id; stream-job parallelism matches partition count. Collectors are stateless. OLAP ingestion scales per topic partition; queries scale with historical nodes.

Load-shed deliberately: under pressure, drop the 1% no-bid sample first, never billable events.

Failure modes

What breaksBlast radiusMitigation
Profile store slow / downEvery bid waits on the lookup → mass timeouts.Hard 3–5 ms timeout and a circuit breaker; fall back to contextual-only bidding. Lower win quality beats zero bids.
Bidder node diesIn-flight requests on that node are lost (≈ a few thousand auctions).Stateless nodes + health checks pull it from rotation in seconds. Its unspent token allocation simply expires with the lease.
Pacing service downNo fresh allocations; risk of overspend or of a full stop.Leased allocations: bidders spend what they hold, then stop. Run pacing as a replicated service with a consistent store behind it.
Stale campaign snapshotA paused line item keeps bidding; a new one never starts.Version every snapshot; bidders report their version; alert on lag; refuse to bid if the snapshot is older than a threshold.

Interviewer asks…

Likely follow-ups. Try answering out loud before you expand each one.

Q1Where is the bottleneck at 1M QPS, and how do you find it?

BOTTLENECKS

Follow the request and ask what is shared. Bidders are stateless and scale out, so they are not it. The candidates are:

  • The profile store — the only remote call on the hot path. One slow shard stalls every request routed to it. Mitigate with a strict timeout, replicas, and a small in-process cache for very active users.
  • Network and connection handling — 16 Gbps of JSON. Keep-alive pools, gzip, and early exit (most requests are rejected before any I/O) matter more than faster bid code.
  • Tail latency, not averages — GC pauses and noisy neighbours turn a 10 ms median into a 150 ms p99.

To find it: per-stage latency histograms inside the bidder plus the exchange-reported timeout rate, which is the only number that reflects what the customer sees.

Q2One advertiser generates 30% of events. How do you handle hot partitions in Kafka?

HOT PARTITIONS

It depends on the partition key. If you keyed by campaign_id, that campaign’s partition is overloaded while others idle — consumer lag grows on one partition and you can’t fix it by adding consumers.

  • Key by something high-cardinality — bid_id or event_id — so load is uniform. You lose per-campaign ordering, which aggregation doesn’t need.
  • Aggregate in two stages: pre-aggregate on the evenly distributed key (or a salted key such as campaign_id#0..15) in small windows, then combine partial counts by campaign. The second stage sees thousands of rows, not billions.
  • Keep an eye on skew in the OLAP store too — segment by time first, then hash.
Q3How would you go multi-region?

MULTI-REGION

You have no choice on the serving side: a cross-continent round trip is 100+ ms, so bidders must sit next to each exchange. Run active-active regions, each fully able to bid alone:

  • Campaign config: one primary SQL database, replicated asynchronously to all regions; bidders read the local snapshot.
  • User profiles: replicated per region; most users appear in one region, so asynchronous replication with last-write-wins is acceptable.
  • Budget: the hard part. A central pacing service splits each budget into per-region allocations based on recent traffic and rebalances every few seconds. Regions never call each other to bid.
  • Events: each region has its own Kafka; mirror to a central cluster for global aggregation and billing.

If a region is cut off it spends its last allocation and stops — bounded overspend, no split-brain.

Q4The exchange’s invoice says 1.02M impressions; your system counted 1.00M. How do you reconcile billing?

BILLING RECONCILIATION

Small discrepancies are normal — the two sides count at different moments (auction win vs pixel render) and filter fraud differently. Contracts usually allow a tolerance of a few percent. The job is to keep it small and explainable:

  • Keep raw events immutable in the data lake. Billing is a deterministic batch job over them, never the streaming numbers.
  • Join on a shared key — the bid ID travels through the win notice, the markup and the beacon — and compare with the exchange’s log-level report. Bucket the differences: won-but-never-rendered, duplicates, invalid traffic, late arrivals.
  • Agree on the billable event up front (burl / rendered impression), and on whose count is the source of truth.
  • Alert when the discrepancy for any partner drifts — a sudden jump usually means a broken pixel or a dedup bug, not fraud.
Q5A DSP is having an outage and times out on every request. What does the exchange do?

DSP OUTAGE

For a single auction nothing special: tmax fires and the auction closes without that DSP. The danger is the aggregate — thousands of connections and threads tied up waiting on a dead endpoint.

  • Circuit breaker per DSP: when timeout / error rate crosses a threshold, stop sending. Probe with a trickle of traffic and ramp back gradually once it recovers.
  • Bulkheads: separate connection pools and concurrency limits per DSP so one failure can’t exhaust shared resources.
  • Adaptive throttling in normal operation — QPS sent to each DSP follows its recent response rate.

From the DSP’s side: shed load early (fast 204 under overload is better than a slow bid), and expect the exchange to throttle you for a while after recovery.

Q6How do you guarantee a campaign never overspends its budget?

BUDGET PACING

You can’t guarantee zero without a synchronous global check on every bid, which the latency budget rules out. So aim for a small, bounded overspend and say what the bound is:

  • Central pacing service hands out short-lived token allocations to each bidder. A bidder can only spend tokens it holds.
  • Maximum overspend ≈ outstanding allocations + bids won but not yet reported. Shrink allocations as the budget nears its end.
  • Track pending (won) separately from confirmed (rendered) spend, and stop at ~98% to leave room for in-flight wins.
  • Whatever leaks through is absorbed as a business rule: the platform doesn’t bill beyond the budget.
Q7Why not exactly-once processing for impression counts?

DELIVERY SEMANTICS

Exactly-once inside a stream processor is achievable (checkpoints + transactional writes), but it covers only the Kafka → job → sink segment. A browser retrying a beacon, or a collector retrying a produce after a timeout, still creates duplicates upstream of it — and transactions add latency and coupling.

The robust design is at-least-once delivery plus idempotence: every event carries a unique event_id minted when the bid is created; the stream job deduplicates on it within a TTL window; sinks upsert by key. You get exactly-once results without depending on every hop being transactional. The nightly batch recount catches anything outside the dedup window.

Q8Why a first-price auction? What changes for the bidder?

AUCTION DESIGN

In a second-price auction the winner pays just above the runner-up, so bidding your true value is optimal. But when a request passes through several intermediaries, each running its own auction with opaque floors, buyers couldn’t verify what “second price” meant. First-price is simple and auditable: you pay what you bid.

The cost moves to the buyer: bidding true value now overpays. DSPs add bid shading — a model of the win-price distribution per publisher / slot that picks the lowest bid likely to win. It needs loss feedback (did we lose, and ideally at what price), which is why bid and win logs are worth storing.

Q9The segment cache misses, or a brand-new user shows up. Now what?

COLD START

Never block. A miss returns in the same few milliseconds as a hit, and the bidder falls back to contextual targeting — page category, geo, device, time — bidding lower because it knows less. Campaigns that strictly require an audience segment skip this request.

  • New users: write a minimal profile asynchronously so the next request hits.
  • Cold cache after a deploy or region launch: preload from a snapshot and ramp traffic gradually; watch hit rate before going to 100%.
  • Store down: circuit-break to contextual-only so revenue degrades instead of disappearing.
Q10Where do you put fraud and bot detection?

FRAUD FILTERING

Both places, with different jobs:

  • Inline (pre-bid): only checks that cost microseconds — IP / user-agent block lists, known datacenter ranges, publisher allow lists, simple rate limits. Goal: don’t spend money on obvious junk.
  • Async (post-bid): heavier models over the event stream — click-timing patterns, impossible impression rates per device, traffic-source anomalies. Results feed back as updated block lists, and as refunds / non-billable flags on events already counted.

The tradeoff is latency vs how much fraud you pay for before catching it. Because events are immutable, an invalid-traffic verdict is a new correction event that the billing batch applies.
